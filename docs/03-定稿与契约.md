# 定稿：食光（剩食管家）· 技术契约

> 本文件是并行开发的唯一事实源。任何人（含子代理）改动接口、表结构、目录所有权，必须先改本文并提交。

## 1. 产品

**一句话**：拍一张冰箱照片，几秒内知道「什么快坏了、今天做什么吃」；月底看到「少扔了多少食物、少排了多少碳」。（真实 VLM 实测约 5 秒，不承诺 3 秒）

| 项 | 内容 |
|---|---|
| 主题归属 | 绿色生活 |
| 目标用户 | 独居学生 / 二人小家庭 / 合租青年（做饭频率低、常忘记冰箱里有什么） |
| 真实痛点 | 食材忘在冰箱深处 → 过期丢弃；不知道该买多少；浪费没有反馈 |
| 与竞品差异 | 竞品是「菜谱推荐」，我们是「库存时效管理」：以**过期倒计时**为主轴，菜谱只是消耗手段，闭环落在**浪费率与碳账** |

## 2. MVP 范围

**P0（必须，缺一不可）**

1. 拍照/上传 → VLM 识别食材清单（含置信度）→ **人工校对表单** → 入库
2. 冰箱看板：按剩余天数排序，红/黄/绿三级，支持改数量与到期日
3. 菜谱建议：选食材 → 混合检索 → LLM 排序并给理由 + 引用 + 缺料提示
4. 消耗/丢弃：扣库存、记浪费重量与原因
5. 统计：浪费率、少扔克数、碳当量、等效换算
6. Agent trace 面板：5 步状态可见（understand → plan → retrieve → compose → verify）
7. 无 key 可跑：`mock` 提供方返回录制好的结果，全链路可演示
8. **饮食计划**：识别入库后一键生成 3 天配餐（哪天吃哪道、用掉什么、还缺什么要买）

**P1（有余力）**：周报流式生成、导出图片、语音提问（Web Speech API）、MCP Server 演示页

**不做**：账号体系、多用户、移动端 App、图像生成、模型微调

## 5. 数据模型（SQLite，`apps/server/data/app.db`，不入库）

共 **12 张业务表 + 1 张 FTS5 虚表**（索引与触发器从略，以 `apps/server/app/db/schema.sql` 为准）：

```sql
-- 业务表（12）
items(id PK, name UNIQUE, category, shelf_life_days, carbon_kg_per_kg,
      price_per_kg, avg_grams, storage_tip, unit)
inventory(id PK, item_id, name, qty, unit, grams, added_at, expires_at,
          status,            -- active|consumed|discarded
          image_id, confidence, note, verified_at)
recipes(id PK, title, ingredients JSON, steps JSON, minutes, servings, tags, difficulty)
images(id PK, path, created_at, recognized JSON)
waste_log(id PK, inventory_id, name, grams, reason, carbon_kg, created_at)
reconcile_applied(fingerprint PK, request_id, inventory_id, action, detail JSON, created_at)
events(id PK, kind, payload JSON, created_at)
agent_runs(id PK, kind, state, steps JSON, created_at)
preferences(id PK, text, kind, source, confidence, user_id, created_at, updated_at)
meal_plans(id PK, payload JSON, created_at, updated_at)
chunks(id PK, source, locator, title, body, tokens, created_at)
chunk_vectors(chunk_id PK, model, dim, vec JSON, created_at)

-- FTS5（1）
chunks_fts(title, tokens, body, source UNINDEXED, locator UNINDEXED,
           tokenize='unicode61')
```

时间一律 ISO8601 带时区（`datetime.now().astimezone().isoformat()`），日期比较只用 `date` 部分。

## 6. API 契约（全部前缀 `/api`，JSON，错误体 `{code,message,detail?}`）

### 6.1 健康

`GET /api/health` → `{"ok":true,"provider":"mock","db":"ok"}`

### 6.2 拍照识别

`POST /api/capture/recognize`（multipart：`file` 图片）

```json
{
  "image_id": "img_...",
  "items": [
    {"name":"西兰花","qty":1,"unit":"颗","confidence":0.92,
     "item_id":"broccoli","shelf_life_days":5,"expires_at":"2026-11-20","matched":true}
  ],
  "warnings": ["第 2 项识别置信度较低，请确认"]
}
```

- 置信度 < 0.7 → 计入 `warnings`，前端标黄
- 识别结果**不直接入库**，必须经 `/api/inventory` 确认

### 6.3 库存

| 方法 | 路径 | 说明 |
|---|---|---|
| POST | `/api/inventory` | body `{"image_id"?, "items":[{name,qty,unit,expires_at,confidence?}]}` → `{"added":n,"ids":[...]}` |
| GET | `/api/inventory?status=active` | 返回 `[{id,name,qty,unit,expires_at,days_left,level}]`，`level` ∈ `fresh|soon|urgent|expired` |
| PATCH | `/api/inventory/{id}` | 可改 `qty`/`expires_at`/`note` |
| POST | `/api/inventory/{id}/consume` | body `{"grams"?:number}` → 扣减，扣完置 `consumed` |
| POST | `/api/inventory/{id}/discard` | body `{"reason":"forgot|spoiled|too_much","grams"?:number}` → 写 `waste_log` |

`days_left` = `expires_at - today`（整数，可为负）。分级：`>3` fresh，`2–3` soon，`0–1` urgent，`<0` expired。

**计量口径**：`grams = qty × items.avg_grams`；`carbon_kg = grams/1000 × items.carbon_kg_per_kg`；`money_saved = Σ(consumed.grams/1000 × price_per_kg)`。`saved_grams` = 已 consume 的克数，`thrown_grams` = 已 discard 的克数，`waste_rate = thrown/(thrown+saved)`。

### 6.4 菜谱

```json
  "missing":[{"name":"大蒜","optional":false}],
  "citations":[{"source":"recipe:r_012","locator":"步骤 1-3"}],

}]}
```

### 6.5 统计

`GET /api/stats/summary?range=30d`

```json
{"waste_rate":0.18,"thrown_grams":820,"saved_grams":3400,
 "carbon_saved_kg":5.2,"money_saved":86.0,
 "equivalents":{"car_km":38,"trees_days":120},
 "trend":[{"date":"2026-11-01","thrown":0,"saved":200}]}
```

### 6.6 周报（SSE）

`POST /api/report/weekly` → `text/event-stream`，事件：`{"type":"delta","text":"..."}` … `{"type":"citations","items":[...]}` … `{"type":"done"}`

### 6.7 Agent trace

`GET /api/agent/runs/{id}` → `{"id","state","steps":[{"name":"understand","status":"ok","started_at","ms","summary"}]}`

**每次 `/api/recipes/suggest` 必须创建一条 `agent_runs`，返回体带 `run_id`。**

### 6.8 饮食计划（识别入库后的下一步）

`POST /api/plan/meals` body `{"days":3,"servings":1,"max_minutes":30}`

```json
{"plan_id":"plan_...","run_id":"run_...",
 "days":[{"date":"2026-11-16","meals":[
   {"slot":"午餐","recipe_id":"r_002","title":"蒜蓉西兰花","minutes":12,
    "uses":[{"name":"西兰花","qty":1,"unit":"颗"}],
    "missing":[{"name":"大蒜","optional":true}],
    "citations":[{"source":"recipe:r_002","locator":"步骤 1-4"}]}]}],
 "shopping":[{"name":"鸡蛋","qty":6,"unit":"个","reason":"2 道菜需要，库存只剩 2 个"}],
 "coverage":{"used_items":6,"expiring_used":2,"unused_expiring":1},
 "warnings":[]}
```

规则（也是 verify 的判定条件）：
1. **过期食材绝不进计划**，只在 `warnings` 里提示「先处理」
2. 同一食材跨餐累计用量不得超过库存数量
3. 每餐必须挂真实 `recipe_id` 与 `citations`
4. 优先消耗 3 天内到期的食材（`coverage.expiring_used` 可核对）
5. 缺料合并成一份购物清单，不得重复列同一食材

Agent 步骤：`understand`（人数/时间约束）→ `plan`（取库存并按到期排序）→ `allocate`（按天分配，控制用量）→ `compose`（生成配餐与理由）→ `verify`（上面 5 条），trace 落 `agent_runs`。

### 6.9 对话改计划（同一个 plan 上迭代）

`POST /api/plan/meals/{plan_id}/revise` body `{"instruction":"第二天想吃清淡点，别放鸡蛋"}`

```json
{"plan_id":"plan_...","run_id":"run_...",
 "days":[ ...同 §6.8 结构... ],
 "shopping":[...],
 "coverage":{...},
 "changed":[{"date":"2026-11-17","slot":"午餐","from":"番茄炒蛋","to":"清炒时蔬","reason":"去掉鸡蛋、改清淡"}],
 "learned":[{"id":"pref_ab12","text":"不吃鸡蛋","kind":"avoid"}],
 "warnings":[]}
```

规则：
1. 只允许改**指定 plan** 的餐次，未涉及的餐保持不变（diff 必须能对上）
2. 指令与已记住的硬性偏好冲突时，以**用户本次指令**为准，但要在 `warnings` 提示冲突
3. 改动必须仍满足 §6.8 的五条规则（过期不入、用量不超、引用非空、优先临期、缺料去重）
4. `changed` 为空说明没改成，必须给出可读原因，不许静默返回原计划

### 6.10 用户偏好（进知识库，跨会话生效）

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/preferences` | `{"items":[{"id","text","kind","source","confidence","created_at"}]}` |
| POST | `/api/preferences` | body `{"text":"不吃香菜","kind":"avoid"}`，手动添加 |
| DELETE | `/api/preferences/{id}` | 用户删除错误推断（必须支持，这是可控性底线） |

- `kind` ∈ `avoid|like|time|portion|health`；`source` ∈ `dialog`（从对话推断）| `manual`
- 偏好写入后**同步进 FTS 索引**，`source=pref:<id>`，可被检索与引用
- 生成计划时必须注入全部偏好：`avoid` 为硬约束（verify 阶段校验），其余为软约束
- 推断出的偏好 `confidence < 0.6` 不展示为已生效，只在 `warnings` 里提示「可能记住」

```sql
preferences(id TEXT PK, text TEXT, kind TEXT, source TEXT,
            confidence REAL, user_id TEXT, created_at TEXT, updated_at TEXT)
meal_plans(id TEXT PK, payload TEXT, created_at TEXT, updated_at TEXT)
```

### 6.11 小票识别（批量入库）

`POST /api/capture/receipt`（multipart：`file` 小票/外卖单/购物截图）

```json
{"image_id":"img_...",
 "items":[{"name":"西兰花","qty":1,"unit":"颗","price":6.5,"confidence":0.88,
           "item_id":"broccoli","shelf_life_days":5,"expires_at":"2026-11-20","matched":true}],
 "purchased_at":"2026-11-15",
 "total_price":23.6,
 "warnings":[]}
```

- 与拍照识别共用入库接口：确认后 `POST /api/inventory`，`added_at` 用 `purchased_at`
- 价格识别不出来的项 `price` 返回 `null`，不得编造
- 小票上的商品名同样走别名表匹配，未命中标 `matched:false`

### 6.12 备菜流水线（多道菜的并行顺序）

`POST /api/cook/sequence` body `{"recipe_ids":["r_002","r_001"],"start_at":"18:30"}`

```json
{"total_minutes":28,
 "steps":[{"order":1,"at":"18:30","action":"烧一锅水","minutes":0,"parallel_with":[]},
          {"order":2,"at":"18:31","action":"腌鸡胸肉","minutes":8,"parallel_with":[1]}],
 "tips":["先烧水可以省 5 分钟"],
 "warnings":[]}
```

规则：步骤必须来自所选菜谱的真实步骤（可合并同类动作）；总时长不得小于最长单道菜；模型不可用时按「耗时降序 + 预处理优先」的规则版排序。

### 6.13 库存对账（智能食材对比）

`POST /api/inventory/reconcile`（multipart：`file` 冰箱照片）

```json
{"image_id":"img_...","checked_at":"2026-11-15T18:20:00+08:00",
 "missing":[{"inventory_id":"inv_1","name":"生菜","qty":1,"unit":"颗","days_left":1}],
 "reduced":[{"inventory_id":"inv_2","name":"鸡蛋","from_qty":6,"to_qty":2,"unit":"个"}],
 "added":[{"name":"酸奶","qty":2,"unit":"杯","confidence":0.83,"matched":true}],
 "suspect":[{"inventory_id":"inv_3","name":"菠菜","reason":"外观异常/无法看清"}],
 "warnings":[]}
```

`POST /api/inventory/reconcile/apply`

```json
{"request_id":"req_ab12cd34",
 "missing":[{"inventory_id":"inv_1","action":"discarded","reason":"spoiled"}],
 "reduced":[{"inventory_id":"inv_2","qty":2}],
 "added":[{"name":"酸奶","qty":2,"unit":"杯"}]}
```

返回 `{"applied":{"discarded":1,"consumed":0,"updated":1,"added":1},"warnings":[]}`

规则：
1. 只比对 `status=active` 的库存；识别置信度 <0.7 或看不清的进 `suspect`，**不得直接判 missing**
2. 默认动作是 `keep`，**任何删除都必须用户确认**（AI 不擅自改数据）
3. `missing` 的 `action` ∈ `consumed|discarded|keep`；`discarded` 走浪费账（写 `waste_log`）
4. apply 幂等：同一 `request_id` 重复提交只生效一次（`request_id` 可选，缺省由服务端生成、只在该请求内去重）；不同 `request_id` 的相同动作视为用户确实又做了一次，正常生效；先全量校验再单个事务落库，任一项非法整批不改数据
5. 对账动作写 `events(kind=reconcile)`，可回溯「哪次核验改了什么」

### 6.14 数据新鲜度（防止用旧数据规划）

- `inventory` 增 `verified_at`：入库、对账、consume/discard 时刷新
- `GET /api/inventory` 每项返回 `stale_days`（距上次核验的天数）
- `recipes/suggest` 与 `plan/meals` 必须检查：存在 `stale_days > 3` 的 active 项时，响应 `warnings` 追加「有 N 样食材超过 3 天未核验，建议先拍一张对账」
- 该提示是**必须出现**的（不允许静默用旧数据规划），但不阻断生成

### 6.15 流式接口（感知性能）

为消除长等待，计划与推荐提供 SSE 版本；非流式接口保持不变（兼容旧调用）。

| 方法 | 路径 | 说明 |
|---|---|---|
| POST | `/api/plan/meals/stream` | body 同 §6.8 |
| POST | `/api/recipes/suggest/stream` | body 同 §6.4 |

事件协议（`text/event-stream`，每条 `data: {json}`）：

```json
{"type":"step","name":"plan","status":"ok","ms":12,"summary":"取临期 8 项"}
{"type":"delta","text":"正在按到期顺序排…"}
{"type":"result","payload":{ ...与对应非流式接口的响应体完全一致... }}
{"type":"error","code":"plan_failed","message":"读取库存失败"}
```

规则：
1. `step` 与 `agent_runs.steps` 一一对应（同名同顺序），前端据此逐步点亮时间线
2. 中途失败必须发 `error` 事件并以 `done` 结束，不能让连接悬挂
3. `result.payload` 必须与非流式接口逐字段一致（前端可用同一套渲染）
4. 客户端断开（AbortController）时服务端必须停止后续模型调用

### 6.16 新手引导（纯前端）

首次进入展示 4 步引导，之后以 `localStorage['shiguang.tour.v1'] = 'done'` 不再出现；每步可跳过，设置里可「重新观看」。

## 8. RAG 设计

| 项 | 方案 |
|---|---|
| 语料 | 菜谱（30+）、保存技巧（分条）、食材保质期表 |
| 分词 | 中文按 **2-gram** 切分写入 `tokens` 列（解决 FTS5 中文分词问题） |
| 索引 | SQLite FTS5（`unicode61`），字段 `title/tokens/body` |
| 检索 | BM25（FTS5 `bm25()`）；若 `EMBEDDING_PROVIDER != none` 追加向量召回，用 **RRF** 融合（k=60） |
| 引用 | 每个 chunk 带 `source`（`recipe:<id>` / `tip:<n>`）+ `locator`（步骤/段落），API 原样返回，前端点角标弹原文 |
| 兜底 | 检索为空时不编造，返回「库存里没有匹配菜谱」 |

## 9. Agent 流水线（`recipes/suggest` 内部）

| 步 | 名称 | 干什么 | 失败处理 |
|---|---|---|---|
| 1 | `understand` | LLM 解析意图与约束（时间/口味/人数） | 降级：直接按输入参数 |
| 2 | `plan` | 工具调用 `list_inventory(sort=expiry)` 取临期 top-k | 失败即报错 |
| 3 | `retrieve` | 工具调用 `find_recipes(ingredients, max_minutes)` | 空结果返回空态 |
| 4 | `compose` | LLM 排序 + 生成 reason（必须引用上一步 id） | 降级：按 BM25 分数排序，reason 用模板 |
| 5 | `verify` | 规则校验：引用 id 存在、食材在库存、步骤 ≥3 | 不过则重试 1 次，仍不过则剔除该条 |

工具注册表（Function Calling schema 放 `app/core/tools.py`）：`list_inventory` / `find_recipes` / `get_shelf_life` / `estimate_carbon` / `log_consumption`。

**MCP**：`mcp/server.py` 用 stdio JSON-RPC 暴露 `search_recipes` 与 `get_shelf_life` 两个工具，附 `docs` 里的启动命令与调用示例（录视频时现场调一次）。

## 10. 安全与兜底（对应评分 4 分，必须有可见证据）

1. 识别结果一律人工确认，不入库不扣库存
2. 每条 AI 结论挂引用；无依据时明说「资料里没有」
3. 置信度可视化（置信度条），低置信度黄标
4. 内容过滤：识别出的名称不在食材库 → 标 `matched:false`，不让它进碳账
5. 失败降级：模型不可用 → 规则版结果 + 顶部提示条（不静默、不假装成功）
6. 免责声明：首页页脚 + 统计页「碳当量为估算，基于公开因子表」
7. 密钥只从 `.env` 读，日志脱敏

## 11. 编码规范（全项目）

- 禁止硬编码盘符/绝对路径，路径从 `Path(__file__).parent` 推导
- 端口/阈值/URL/模型名集中在文件顶部全大写常量
- Python：类型标注、`pydantic` 模型做输入输出、不用 `print`（用 logging）
- TS：`strict: true`，禁止 `any`，API 类型集中在 `src/lib/api/types.ts`
- 组件一文件一组件，CSS Modules 同名，单文件 ≤200 行
- 中文注释可写，标识符英文
