# 08 答辩问答（预设 12 问）

> 用法：每题先给一句结论，再给 3 条支撑。**先说结论，再补证据**，不要从头讲背景。
> 原则：能承认的短处当场承认（估算、误识别、无账号），然后用设计说明已经兜住了。

---

## Q1 拍照识别不准怎么办？

**结论**：识别不准是我们设计的**前提**，不是意外。

- 识别结果不直接入库，先进可编辑表单，人确认后才写库存。
- 每项带置信度条，低于 0.7 标黄并在顶部汇总提示「第 2 项请确认」。
- 名称不在食材库的，标 `matched:false`，不允许进碳账与浪费率，避免脏数据污染统计。

---

## Q2 碳排数据可信吗？

**结论**：不可信到「核查」级别，可信到「比较与激励」级别，误差 ±30% 写在页面上。

- 因子来自公开文献（Poore & Nemecek 2018、OWID 食物碳排数据集），同一食材多来源取均值，不是我们拍的。
- 口径明确：kg CO₂e / kg 可食部，覆盖生产到零售，不含家庭冷藏与烹饪。
- 用途边界写死：不做碳核查、碳交易、企业披露；等效换算用公开常量（0.137 kg/km、一棵树 16 kg/年）。

---

## Q3 和普通菜谱 App 有什么区别？

**结论**：它们从「我想吃什么」出发，我们从「什么快坏了」出发。

- 主轴是**过期倒计时**（按剩余天数排序、红黄绿分级），菜谱只是消耗库存的手段。
- 闭环落在**浪费率与碳账**：吃掉多少、扔掉多少、为什么扔，月底给一张能核对的账。
- 交互上主入口是拍照与卡片，不是聊天框；推荐结论挂引用角标，能点回菜谱原文。

---

## Q4 为什么不训练模型？

**结论**：72 小时工期 + 无标注数据，微调是负收益；我们把不确定性做进了产品。

- 没有食材图像标注集，微调的收益无法验证，风险却全在演示当天。
- 通用 VLM + 结构化输出 + 校验重试，配合人工校对表单，工程上更稳。
- 反过来说，即便模型更准，人工确认这一步也不能省——误识别会直接污染碳账。

---

## Q5 Agent 是不是套壳？

**结论**：套壳的特征是「一次请求一次回答」，我们是五步状态机且可回放。

- 五步：意图理解 → 规划 → 检索 → 生成理由 → 自检；每步落库，页面显示耗时与摘要。
- 工具调用走统一注册表（`list_inventory` / `find_recipes` / `get_shelf_life` / `estimate_carbon` / `log_consumption`）；页面 trace 只展示步骤名、状态、耗时与一句摘要，**不展开**每次调用的参数与返回条数。
- 第五步是硬校验：引用 id 必须存在、食材必须在库存、步骤 ≥3，不过则重试一次，再不过就剔除该条。
- 其中 `search_recipes` 与 `get_shelf_life` 另包了一个 MCP Server（stdio JSON-RPC），终端可现场调用。

---

## Q6 RAG 检索不到怎么办？

**结论**：明确说「没有」，不编。

- 检索为空时返回空态文案「库存里没有匹配菜谱」，不给推荐卡片。
- 当前实现是 FTS5（BM25）+ 可选向量的 RRF 融合；`find_recipes` 只用 `max_minutes` 做时长过滤，**没有实现多级「先窄后宽」放宽**，答问时如实说明。
- 绝不走「让模型自由发挥」这条路——没有 chunk 就没有引用，没有引用就不许出结论。

---

## Q7 如何防 Prompt 注入？

**结论**：把用户输入当**数据**，不当指令；把模型输出当**不可信输入**，全部校验。

- 用户图片/文本只进 user 角色并加分隔标记；系统提示集中在常量里，靠 Git 追溯；注入无法改写工具白名单（只有 5 个，参数有类型校验）。
- 输出必须过 JSON Schema + pydantic 校验，字段白名单，多一个字都不落库；失败重试 1 次，再失败降级规则版。
- 渲染层只做纯文本渲染，不解析模型返回的 HTML/Markdown；引用 id 不在库里就不显示。
- 识别出的名称必须命中食材库，否则 `matched:false` 且不进统计——这是最后一道闸。

---

## Q8 商业化怎么做？

**结论**：C 端不收费，钱在 B 端的**损耗管理**。

- C 端做口碑与数据：免费、无账号、本地存储，降低使用门槛。
- B 端卖给高校食堂 / 生鲜店 / 社区团购：同一套「临期倒计时 + 损耗率看板」，按门店订阅。
- 碳账可对接企业员工绿色行动/ESG 活动，作为参与度工具，但**不卖用户数据**、不做碳资产交易。

---

## Q9 72 小时怎么完成的？

**结论**：契约先行 + 并行分角色 + mock 先跑通 + 每个切片可验收。

- 先定契约（API/表结构/目录所有权），把工程切成 A–F 六个互不越界的角色并行开工；mock 提供方先跑通全链路。
- 业务闭环：库存、检索、Agent trace、统计落库，刷新不丢；随后三轮独立审查修阻塞项。
- 代码与文档交付集中在 11-15 下午完成；剩余时间用于 PDF、演示脚本、录制与提交校验，P1 功能全程可砍。

---

## Q10 隐私与照片怎么处理？

**结论**：没有账号，就没有身份数据；照片只在本机。

- 无登录、无手机号邮箱、无第三方统计 SDK；图片只写本地 `data/upload/`，随数据目录被 gitignore。
- 图片不用于训练、不二次分发；演示与视频里的照片全部自摄，不用任何用户照片。
- 需要披露的一点：使用真实 provider 时图片会发送到模型服务商 API；`mock` 模式完全不出网，README 里写清。

---

## Q11 模型成本多少？

**结论**：演示期总成本个位数到十几元，且可降到 0。

- 调用是稀疏的：只有拍照识别（1 图 + 短提示）和推荐（约 3k token）走模型，看板与统计纯本地计算。
- 默认走 flash 档文本模型 + 轻量视觉模型；`mock` 模式成本为 0，答辩现场可用。
- 规模化后的降本路径：识别结果按图片哈希缓存、推荐结果按库存指纹缓存，重复请求不打模型。

---

## Q12 如果模型挂了怎么办？

**结论**：降级，不报错，并且**明确告诉你降级了**。

- 运行期两层兜底：JSON 校验失败重试 1 次 → 再失败转规则版结果（BM25 排序 + 模板理由 + 明确 `warnings`）。
- `mock` 接管发生在启动/构造 provider 时：provider 未知、缺 key 或 base_url 不可用会回退 `mock` 并打日志；运行中模型报错走规则版降级，不会临时切 `mock`。
- 页面顶部黄色提示条说明「当前为降级模式」；密钥只从环境变量读、日志脱敏；异常统一转 502 + 人话提示，不向前端抛堆栈。

## 附：三个「不要踩」的坑

| 坑 | 说法 |
|---|---|
| 别说「我们的碳数据准确」 | 说「估算，±30%，用于比较」 |
| 别说「识别率 99%」 | 说「识别后必须人工确认」 |
| 别说「AI 全自动完成」 | 说「人定契约与验收，AI 写实现」 |
