# 04 技术方案 · 食光（剩食管家）

> 技术文档 PDF ≤30 页。函数名、接口、数值取自当前代码与实测记录；未实现项在 §9 明说。
> 基线：`apps/server`（FastAPI + SQLite）+ `apps/web`（React 18 + TS + Vite），104 项 pytest 全绿。

## 1. 一页摘要

| 项 | 内容 |
|---|---|
| 问题 | 食材过期丢弃。菜谱 App 只管「想吃什么」，没人管「冰箱里什么快坏了」；浪费没有反馈 |
| 方案 | 先管时效再谈菜谱：拍冰箱 → 校对入库 → 临期倒计时 → 配餐消耗 → 浪费/碳账。中途可拍小票批量入库、拍第二张对账、一句话改计划 |
| 形态 | 6 个路由的单页 Web，主入口是拍照与卡片；唯一对话入口是计划页底部「改计划」框 |
| 关键技术 | Provider 抽象 + JSON 模式 + pydantic + 重试 1 次 + 规则降级；双五步状态机轨迹落库；2-gram + FTS5 BM25 + 可选向量 RRF + 引用回链；三入口视觉识别与三形态归一；AI 不直接改数据；5 工具 + MCP stdio |
| 规模 | 20 接口；12 实体表 + 1 张 FTS5 表；食材 69 / 菜谱 30 / 技巧 20 段 / 别名 49；前端 6 页 + 21 个基础组件；104 项测试 |
| 结果 | 真实 `glm-4v-flash`：4 项 / 4.98 s。mock 复跑：计划 85 ms（6 餐、用掉 6 项、临期 3 项）、改计划 184 ms（4 处）、对账 4 不见/3 新增/1 待确认、30 天浪费率 16.3%、首屏 64.4 KB gzip |
| 我的判断 | 技术价值不在「调通模型」，在**把不确定性做成可校对流程**：识别必校对、结论必带引用、失败必降级且可见、改数据必留痕。代价多一步确认，收益是误识别不污染碳账 |

## 2. 需求与场景

| 场景 | 触发与动作 | 系统要给出 |
|---|---|---|
| 买完菜 / 下班前 | 拍冰箱、拍小票；看首页倒计时 | 清单 + 到期日 + 置信度；临期排序 + 立刻能做的菜 + 缺料 |
| 周末备餐 / 不合口味 | 生成 3 天计划；一句话改计划 | 哪天哪餐、用掉什么、缺什么；只改点名餐次 + diff + 原因 + 记住偏好 |
| 隔几天核对 / 月底复盘 | 再拍一张对账；打开浪费账本 | 不见/变少/新增/看不清，默认全保留；浪费率、克数、碳、金额、趋势 |

目标用户：独居学生、二人小家庭、合租青年（做饭频率低、一次买几天、不记账）。现有方案为什么不够：菜谱 App 不知道你冰箱里有什么，推荐可能全缺料；备忘录要手输、不算到期、不算账；记账 App 只管买不管扔；通用聊天助手结论无出处、无法落库。明确不做：账号、多用户、App、微调、图像生成、营养处方、扫码、常驻摄像头。

## 3. 总体架构

| 层 | 目录 | 职责 | 红线 |
|---|---|---|---|
| 表现层 | `apps/web/src` | 6 页、22 个基础组件、设计令牌、错误态 | 不写业务规则 |
| 装配 + 接口 | `main.py`、`api/` | 中间件、挂路由、Pydantic、状态码、统一错误体、静态托管 | 只 import，不写 SQL |
| 领域 + 检索 | `domain/`、`rag/` | 计量、状态机、对账、偏好、账本；2-gram、索引、混合检索、引用 | 不依赖 FastAPI |
| 基础设施 | `core/`、`db/`、`mcp/` | Provider、工具表、SSE、安全、连接迁移；stdio JSON-RPC | 不含业务名词 |

请求路径：浏览器 → `SecurityMiddleware`（Basic Auth → 限流 → 8 MB 上限）→ `api/`（Pydantic）→ `domain/`（调 `core/provider`、`core/tools`、`rag/`）→ `db/conn.py`（WAL、单事务）→ JSON / SSE。

| 决策 | 为什么 | 不这么做会怎样 |
|---|---|---|
| 单 uvicorn worker | 单用户写并发低；1.6 GB 内存只够一个进程 + 模型调用 | 多 worker 抢 SQLite 写锁，限流桶与 provider 单例要改 Redis |
| SQLite（标准库，不 ORM） | 备份=拷文件；FTS5 自带检索；零外部服务 | 多一个 PG 进程、连接池、迁移，现场多一个故障点 |
| WAL + `busy_timeout=30s` + `BEGIN IMMEDIATE` | 读写不互斥；批量对账一次拿写锁 | 默认 journal 下批量写易超时 |
| 托管 `dist` + `current` 软链 + `shared/upload` | 少一个 nginx；回滚只改链接；上传目录外挂（`capture/recognize` 待收敛，见 §9） | 覆盖式部署无法回滚，切软链后旧图 404 |

## 4. AI 能力设计

> 对应评分六项：大模型集成 8 / Agent 8 / RAG 6 / 多模态 5 / AI 安全 4 / 工具 4。

### 4.1 大模型集成

| 机制 | 实现 |
|---|---|
| Provider 协议 | `LLMProvider`：`chat_json`/`chat_text`/`chat_vision`/`stream_chat`；5 预设 `mock`/`zhipu`/`dashscope`/`openai`/`local`，全走 OpenAI 兼容 `/chat/completions` |
| 结构化输出 | `json_object` → `extract_json`（容忍围栏、寒暄、裸数组）→ pydantic `model_validate`；失败重试 1 次，再失败 `llm_invalid_json`(502) |
| 视觉归一 | 实测裸数组 / `{items}` / `{"items":[{"items":[…]}]}` 套娃 → `_normalize_vision_payload` 递归拍平，保留 `purchased_at`/`total_price` |
| 兜底 | 上游不支持 `response_format` 去掉重发一次；`ConnectError` 重试 1 次（0.8 s，治 Windows TLS 握手）；文本 60 s / 视觉 90 s；`SSL_VERIFY` 取 `os`/`strict`/`off`；非 local 且 key 空 → 启动回退 mock 并告警 |

Prompt 版本化：Prompt 是模块顶部常量（`VISION_PROMPT`、`RECEIPT_PROMPT`、`RECONCILE_PROMPT`、`UNDERSTAND_SYSTEM`、`COMPOSE_SYSTEM`、`REVISE_SYSTEM`、`LEARN_SYSTEM`、`COOK_SYSTEM`、`report.SYSTEM_PROMPT`），靠 Git 与 `CHANGELOG.md` 追溯；**没有独立 `prompts/` 目录与版本号**，`PLAN.md` 这条承诺未落地。

为什么：模型输出是不可信输入，全部走「提取→校验→重试→降级」一条管道。不这么做：套娃返回直接 500、`confidence:92` 撑爆置信度条、上游抖一下整天演示全挂。

### 4.2 Agent 工作流

| 步 | 菜谱建议（`recipes_suggest`） | 配餐/改计划（`meal_plan`） | 失败策略 |
|---|---|---|---|
| 1 understand | 人数/时长/口味 | 天数/人份/上限；改计划解析 `ReviseIntent` | 按输入参数继续，标「已降级」 |
| 2 plan | `list_inventory` 取临期 top-10 | top-50，剔过期、合并同名多批、注入偏好 | `plan_failed`(500)，trace 记 error |
| 3 retrieve/allocate | `find_recipes` | 候选 12 道 + 贪心草案 | 空结果 → 空态，后续 skipped |
| 4 compose | LLM 排序 + 理由，只能从候选选 | LLM 排餐，不足用 `_fill_from_greedy` | 规则版 + `DEGRADE_WARNING` |
| 5 verify | 引用 id 在检索结果内、步骤 ≥3 | 5 条规则独立复算；重试→贪心重排→剔坏餐 | 降级/剔除写 `warnings` |

trace：`agent_runs(id,kind,state,steps JSON,created_at)`，步骤固定 `{name,status,started_at,ms,summary}`，`state∈running|ok|degraded|failed`；`GET /api/agent/runs/{id}`；前端 `AgentTracePanel` 展开才懒加载。为什么：让「用了 Agent」可验证；降级与模型版同结构。不这么做：一次超时就 500，或模型编个不存在的菜谱 id 页面照样渲染。

### 4.3 RAG

| 项 | 实现 |
|---|---|
| 语料与切分 | 菜谱 30 + 技巧 20 段 + 偏好；一道菜一 chunk：`recipe:<id>`/`步骤 1-N`/`食材+步骤`；技巧 `tip:<n>`；偏好 `pref:<id>` |
| 分词与索引 | 中文 2 字滑窗（`西兰花→西兰/兰花`），英文数字整段小写；FTS5 `unicode61`（`title/tokens/body`），`tokens` 存 2-gram 串 |
| 召回与融合 | `bm25(…,10,8,1)` 候选 limit×3；可选 `/embeddings` 向量缓存 `chunk_vectors`；RRF `k=60`，归一 `rel` + `matched_by` |
| 引用与空态 | `{source,locator,text≤120字}`；`_sanitize_citations` 只留本次检索真实存在的键，编的丢弃，没给用候选自带引用兜底；检索为空返回 `[]`，前端不出卡片 |

为什么 2-gram：`unicode61` 不切中文，整句入库只能整句匹配。为什么 RRF：BM25 无上界、余弦 [-1,1]，量纲不同，RRF 只看名次免调权重。为什么引用带 text：角标立刻看到原文，引用变成可核对数据。不这么做：结论无法验证，或 `recipe:r_999` 也能显示成能点的角标。

### 4.4 多模态

| 入口 | Prompt 约束 | 输出 |
|---|---|---|
| `/api/capture/recognize` | 中文名；数量看不清给 null；置信度分档（清晰 0.85–0.95 / 遮挡 0.5–0.7 / 靠猜 <0.3） | + `item_id`、`expires_at`、`matched` |
| `/api/capture/receipt` | 逐行；`price` 认不出必须 null；无合计/日期给 null | + `purchased_at`、`total_price`；中文字段名折标准键 |
| `/api/inventory/reconcile` | 数清能看清的；看不清加「看不清：」并压到 <0.5；不许编造 | 识别项 → 与 active 库存比对 |

图片：前端限 8 MB（`MAX_UPLOAD_BYTES` 单一来源），中间件按 `Content-Length` 拦 413，接口内再按字节拦一次；小票与对账落盘 `SHIGUANG_UPLOAD_DIR`，`capture/recognize` 仍写 `apps/server/data/upload`（未收敛，见 §9）；`images` 表存相对路径 + 识别 JSON，可回溯「当时识别成什么」。

为什么：三个入口共用一条视觉链路，归一化只写一处，新入口只需换 Prompt 与字段映射。不这么做：三种返回姿势各写一套解析，必有一处漏字段或漏价格，mock 与真实模型行为还会分叉。

没做的：语音播报/提问（P1 砍掉）、图像生成、多图拼接、专用 OCR；图表是手写 SVG，属可视化，答辩别混着说成生成式多模态。

### 4.5 AI 安全与可控

| 措施 | 实现 | 不这么做会怎样 |
|---|---|---|
| 识别不入库 | 只写 `images`，入库必须 `POST /api/inventory` | 一次误识别污染碳账与浪费率 |
| 置信度分级 | <0.7 进 warnings + 黄标；对账 <0.7 进 `suspect`，不判 missing | 「看不清」被当成「吃掉了」 |
| 库外 / 过期 | `matched:false` 标「不计碳账」；推荐/计划先剔 `days_left<0` 只提示 | 默认因子算假碳账；过期菜被排进计划 |
| 忌口硬约束 | 从偏好文本独立抽词（`不吃鸡蛋→鸡蛋`）+ 库存名/配料名求交，命中整道排除，verify 再查 | 忌口食材不在库存时硬约束整条失效 |
| 偏好与降级 | <0.6 只存不生效；偏好可删；冲突以本次指令为准；降级统一「已降级：」前缀写 warnings 并展示 | 误推断永久生效；用户以为吃的是模型结果 |

### 4.6 工具集成

5 个工具（schema 均 `additionalProperties:false`）：`list_inventory`（`sort∈{expiry,added,qty}`、`status`、`limit 1–50`，临期优先）、`find_recipes`（`ingredients[]` 必填、`max_minutes 1–240`，走 RAG 返回带 `source/locator` 的候选）、`get_shelf_life`（`name`、`storage`，未命中明说「不编造」）、`estimate_carbon`（`grams` 必填，与账本同口径）、`log_consumption`（`inventory_id`、`action∈{consume,discard}`，复用 `inventory.consume`）。

`register_all()` 幂等注册；`call()` 对未注册/参数不匹配/异常统一返回 `{error,tool,…}` 不抛异常，业务层另有本地直调兜底。MCP：`mcp/server.py` 独立进程，stdio JSON-RPC 2.0（`initialize`/`tools/list`/`tools/call`/`ping`），暴露 `search_recipes`、`get_shelf_life`，参数白名单过滤，异常返回 `isError:true` 不断流。为什么不直接让模型写 SQL：白名单 + 类型校验，模型只能在这 5 个动作里选。

## 5. 业务正确性

### 5.1 计量（唯一实现：`domain/inventory.py`）

| 量 | 公式 / 规则 |
|---|---|
| 克数 | `grams=qty×avg_grams`；改数量重算；食材库缺失用 200 g |
| 碳 / 金额 | `grams/1000×carbon_kg_per_kg`；`grams/1000×price_per_kg` |
| 部分消耗 | `take=min(grams,remaining)`；qty 按 `left/total` 比例折算（round 3），只改 grams 会让 qty 脱节 |
| 浪费率与换算 | `thrown/(thrown+saved)`（saved 来自 `events(kind=consume)`）；`carbon/0.15` km、`carbon/0.06` 树·天；**与 `docs/06` 的 0.137/16 kg·年 不一致，待统一（§9）** |

状态机：`active|consumed|discarded`；consume/discard 只允许 active（否则 409）；扣到 0 转终态；每次刷新 `verified_at`；discard 必须给 `reason∈forgot|spoiled|too_much`；两者都带 carbon/money，食材表改价不影响历史账。

### 5.2 计划生成的 5 条硬规则

1. `_split_inventory`：usable/expired 分开，同名多批合并数量与克数（否则两批生菜 1+2 只认 2 颗）；
2. 偏好：`avoid` 抽词 × 库存名 × 候选配料名，命中整道排除；
3. 候选：RAG 12 道，过滤步骤 <3；
4. 贪心 `_score=3.0×临期+1.2×普通−0.8×必买缺料−0.02×分钟−0.6×重复菜−2.5×同上餐+0.5×相关度`；一点库存都用不上取 `-inf`；
5. 落成：逐餐扣库存，超量转 `missing`，缺口合并 `shopping`（可选调味料不列）。

verify 独立复算：过期不入、累计不超库存、每餐真实 `recipe_id` 且 citations 非空、临期优先、采购清单去重且必买齐全。不过 → 带 hint 重试 1 次 → 贪心重排 → 剔坏餐 → 仍有问题写 warnings 且 `state=degraded`。

### 5.3 改计划的 diff 语义

| 规则 | 实现 |
|---|---|
| 只改点名餐次、不许漂移 | `_target_keys` 解析目标集合，其它餐沿用存档 `uses/missing`（`frozen_keys`）；`_diff_days` 按 `(date,slot)` 比对 `recipe_id`+`uses`+`missing`，diff 出现未点名餐次 → **整次放弃** + 原因 |
| 点名菜做不到要说明 | `_swap_failure_reason` 区分：库里没有 / 超时长 / 含忌口 / 现库存做不了；前缀「没能换成X：」 |
| 冲突与用量 | 本次指令与旧 `avoid` 冲突时以指令为准并提示；未涉及餐沿用存档用量，`_overclaim_warnings` 写明「库存 X，计划累计 Y」 |
| 没改成也有话说 | `changed=[]` 返回「指令里没有能落到这份计划上的改动（意图摘要）」，前端显示原因 |

### 5.4 对账

比对（只读 `build_diff`）：识别项同名合并、置信度取最高；匹配 `item_id` → 同名 → 名称互含取最长名组（「番茄」不命中「番茄酱」）；同名多批按 `expires_at` 升序分配；低置信/看不清进 `suspect` **不判 missing**；覆盖≈0 → missing，部分覆盖 → reduced{from,to}；识别多于库存只给 warning；空识别全部保留。

落地（`apply`）：`request_id` 缺省服务端生成；`checked_at` 非法/未来收敛到当前；**先全量校验** → 幂等指纹 `request_id+action+inventory_id+目标值` 查 `reconcile_applied` → 单事务落库（discard→waste_log，consume→events，reduced→同比例改 qty/grams，added→`add_items`）→ 写 `events(kind=reconcile)` → 所有 active 行盖 `verified_at`（否则 stale 提示永不消失）；任一异常整批回滚。为什么两阶段：中途失败若已提交前几行，用户无法判断哪些生效。不这么做：重复点「应用」把同批扔掉记两次，浪费率翻倍。

### 5.5 幂等与事务

`transaction()` 让块内 `get_conn()` 返回同一连接的代理（`commit/rollback/close` 空操作），领域函数自带的 commit 不会提前落盘；`BEGIN IMMEDIATE` 一次拿写锁；`busy_timeout=30s`。老库：`MIGRATION_COLUMNS`/`MIGRATION_INDEXES` 补列补索引；`repair_invalid_times` 清历史非法 `verified_at`，触发器拦新写入（垃圾时间戳 = 假新鲜）。

## 6. 前端工程

| 路由 | 页面与产物 |
|---|---|
| `/` | 首页：倒计时 + 冰箱全景 + 今日建议（10.1 KB） |
| `/capture` | 拍照入库（冰箱/小票/对账，44.0 / 13.8 KB gzip） |
| `/plan` | 3 天计划 + 改计划 + 偏好（18.3 / 7.2 KB） |
| `/cook`、`/stats`、`/report` | 今天吃什么 + 备菜时间轴；浪费账本；周报 SSE（15.3 / 8.1 / 5.9 KB） |

6 页全部 `React.lazy`，`react/react-dom/react-router-dom` 单独成块。首屏只加载外壳 + 首页：**191.5 KB raw / 64.4 KB gzip**（index 15.6 + react 164.4 + css 11.5）。为什么分包：改业务不重下 164 KB 框架；不这么做单包 400 KB+，首屏多等 1–2 秒。

组件：`components/ui` 21 个无业务原子（Button/Card/Notice/Skeleton/EmptyState/ConfidenceBar/CitationChip/AgentTrace/StreamProgress…）；`layout` 8 个（含导航表 `nav.ts`）；`tour` 新手引导 3 个（`TourProvider`/`TourOverlay`/`tourSteps`，Esc 可跳过并写 `localStorage`）；`features/<域>` 7 域（capture/plan/cook/dashboard/stats/report/stream，单域 3–38 个文件），纯函数抽 `*.ts`、hook ≤200 行；`lib/api` 类型集中 `types*.ts`。

设计系统：手写 CSS 变量，不引 UI 库/Tailwind/图表库；颜色与分级对齐（urgent 红 0–1 天、soon 黄 2–3 天、fresh 绿 ≥4 天）；环图/趋势图手写 SVG 带 `aria-label`。收益：运行时依赖只有 3 个；代价：组件开发慢。

错误态：传输错误（`network/timeout/http_5xx`）→ `DemoBanner` 说明「后端没应答，下面是内置样例」并标「演示数据」；401/403/413/422 → 专属文案；业务失败（有 `code`）→ 就地显示；渲染异常 → `ErrorBoundary`；加载/空数据 → `Skeleton`/`EmptyState` + 下一步按钮。为什么分传输与业务错误：前者后端没在，可退回样例；后者后端在但这次不行，必须如实报错。

## 7. 测试与验证

104 项、13.36 s 全绿。分布：对账 21、改计划 14、库存 10、API 8、计划 8、偏好 8、推荐 7、备菜 7、RAG 6、分词 6、小票 5、统计 4。隔离：每用例独立 `tmp_path` SQLite；种子指向临时空路径；`FakeProvider` 注入，不打真实模型。

真实模型（`zhipu`/`glm-4v-flash`，`CHANGELOG.md` 2026-11-15）：冰箱实景一张返回 **4 项 / 4.98 s**；同批暴露 ①数量 null ②置信度虚高 1.0 ③三种返回姿势。复测 `python scripts/probe_vlm.py ../../samples/fridge-1.jpg`（打印条数/耗时/置信度，不打印密钥）；素材 `samples/` 7 张自摄照片。其余耗时均为 mock 回放（零网络、确定性），不能当模型延迟指标。

mock 复跑（每条按各自初始状态单独执行：计划/改计划用同一份 seed，对账在另一份 seed 上做，互不叠加；`python scripts/seed_demo.py --reset` → 28 条记录、在库 8 条：菠菜过期 1 天、生菜明天到期、北豆腐 2 天、番茄/香菇 3 天、牛奶 5 天、鸡蛋 20 天、鸡胸肉 60 天）：

| 调用 | 结果 | 耗时 |
|---|---|---|
| `POST /api/plan/meals {days:3}` | 6 餐；`coverage {used_items:6, expiring_used:3, unused_expiring:1}`；采购 11 项；4 条 warnings | 85 ms |
| `POST …/{id}/revise`「第二天清淡点，别放鸡蛋」 | changed 4 处（带 from/to/reason）；learned 2 条（不吃鸡蛋 0.80 / 口味清淡 0.65） | 184 ms |
| `POST /api/recipes/suggest` / `cook/sequence`（2 道） | 3 条推荐 + 引用原文；备菜 10 步 / 21 分钟 / 有 `parallel_with` / 3 条 tips | 52 / 42 ms |

| `GET /api/stats/summary?range=30d`；`POST /api/report/weekly` | 浪费率 0.163（1650÷10120 g）、吃掉 8470 g、碳 48.05 kg、省 114.37 元、car 320 km、trees 801 天；周报 44 个 SSE 事件 | — |

端到端（人工验收）：上传 `samples/fridge-1.jpg` 得 8 条（1 条 0.55 标黄、1 条库外），取消 1 条后确认，入库数=勾选数；首页按 `days_left` 升序、过期在底部、改到期日颜色变、刷新不丢；对账 4 项标「扔掉」→ `discarded=4`、waste_log +4、stale 提示消失；计划里过期菠菜不在任何 uses；改计划后仅第 2 天变动。

## 9. 局限与下一步

| 局限 | 现状与下一步 |
|---|---|
| 模型非确定性 / 依赖光照 | 同图两次可能不同；实测数量 null、置信度虚高 1.0；只留 1 次真实记录。→ 录制当天跑 `probe_vlm.py` 留档、按图片哈希缓存、加「重拍」引导与多图 |

| 单用户 / 单 worker / 向量默认关 | 无登录无多端；单进程并发上限低；默认只有 BM25。→ 不做账号；扩容先换 PG + 外部限流；演示机开 `local`（BGE-M3）对比 |
| 碳因子口径未统一 | 代码 0.15/0.06，`docs/06` 仍 0.137/16 kg·年。→ 二选一并写进验收 |
