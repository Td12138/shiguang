# 10 开发提示词记录（AI 协作过程证据）

> 用途：本文件是「食光」开发过程的 AI 协作留痕，可复现、可审计。
> 记录方式：按角色保存**实际发给子代理的完整提示词**，不做事后美化；一次任务一条，含约束、验收命令与禁止项。
> 提交说明：赛事要求保留开发过程与原创性证据，本文件与 Git 提交历史互为佐证。

## 1. 协作架构

```
主会话（编排者）
 ├─ 写定稿契约 docs/03-定稿与契约.md（接口/表结构/目录所有权）
 ├─ 串行依赖自己做：集成、联调、部署、提交
 └─ 并行子代理（各自锁死目录，互不越界）
      ├─ A 后端基础设施
      ├─ B RAG 与业务域
      ├─ C 前端骨架与首页
      ├─ D 种子数据
      ├─ F 提交材料与答辩
      └─ R 独立审查（只读，输出缺陷清单）
```

分工原则：**能并行的按目录切，不能并行的（接口契约、集成、部署）主会话独占**。每个子代理都拿到同一份契约，因此不靠口头约定对齐。

## 3. A · 后端基础设施

```
你在 Windows 上为一个参赛项目实现后端基础设施层。项目名「食光」，剩食管理 Web 应用。

实现要求：
1. config.py：自写 20 行 .env 解析（不引 python-dotenv）；端口/URL/模型名/阈值集中为全大写常量；
   缺字段按契约默认值补；路径用 Path(__file__) 推导。
2. core/provider.py：实现契约 §7.1 的 LLMProvider 与 get_provider()。
   httpx.AsyncClient + OpenAI 兼容 /chat/completions；预设 zhipu/dashscope/openai/local/mock；
   chat_json 用 response_format=json_object，pydantic 校验，失败重试 1 次后抛 AppError("llm_invalid_json")；
   chat_vision 传 base64 data URI；stream_chat 异步生成器解析 SSE；超时 60s（视觉 90s）；日志不输出 key。
3. core/mock.py：无 key 全链路可跑。chat_vision 优先读 data/fixtures/recognize_fridge.json，
   缺失回退内置样例；chat_json 读 suggest.json；stream_chat 按 2-4 字切片模拟流式。
4. core/tools.py：5 个工具的 function calling schema + register/call 注册表，未注册返回错误而不崩溃。
5. core/errors.py / sse.py / safety.py：AppError、SSE 格式化、脱敏与免责声明常量。
6. main.py：CORS 允许 5274；try/except ImportError 逐个挂载 capture/inventory/recipes/stats/report
   路由（并行开发中可能还不存在）；启动事件调用 init_db（同样容错）；AppError 处理器；启动日志脱敏。
7. requirements.txt / .env.example：只列实际用到的依赖；变量带中文注释。

自检必须实际执行并贴输出：import app.main；打印 provider.name。
```

**设计要点**：模型层只负责「拿到结果或明确失败」，**降级不放在这一层**——避免出现「AI 挂了但假装成功」。这一条直接对应评分表的「AI 安全与可控性」。

## 4. B · RAG 与业务域

```
你在 Windows 上为一个参赛项目实现 RAG 检索层与业务域。

只允许写：app/db、app/rag、app/domain、app/api/{capture,inventory,recipes,stats,report}.py、
          mcp/server.py、tests/。
app/core 由另一代理并行写，只 import 不修改；接口按契约 §7.1。若模块暂时不存在，
让业务函数支持注入（provider=None，内部 provider or get_provider()），测试注入 FakeProvider。

实现要求：
1. schema.sql + conn.py：契约 §5 全部表；get_conn() 返回 row_factory=Row；init_db 幂等并从 app/data 灌种子。
2. seed.py：读 items.json/recipes.json/tips.md（并行生成，可能缺失——缺失只告警不崩溃）；重建 FTS5；
   提供 python -m app.db.seed --force。
3. tokenize.py：中文 2-gram（保留英文/数字），解决 FTS5 中文分词。
4. index.py：FTS5 虚表，chunk 来源=菜谱（recipe:<id>）与技巧（tip:<n>）。
5. retrieve.py：BM25 + 可选向量召回（api/local embeddings），RRF(k=60) 融合，返回 source/locator/score。
6. inventory.py：入库/列表（days_left 与 fresh|soon|urgent|expired 分级）/改/consume/discard；
   grams = qty × avg_grams；discard 写 waste_log 并算 carbon_kg。
7. recipes.py：五步流水线 understand→plan→retrieve→compose→verify，每步写 agent_runs.steps
   （名称/状态/毫秒/摘要）；verify 规则校验（id 必须来自检索结果、步骤≥3），不过重试 1 次，
   仍不过剔除；LLM 不可用降级为 BM25 排序 + 模板理由，并在 warnings 标注「已降级」。
8. stats.py：按契约公式；equivalents 常量置顶（car_km = 碳/0.15，trees_days = 碳/0.06）。
9. report.py：周报优先流式，失败用确定性模板，结束发 citations 事件。
10. api/*.py：严格按 §6 路径与字段；上传存 data/upload（自建目录）；识别结果不入库；
    置信度<0.7 与未匹配项写 warnings；suggest 必须建 agent_runs 并返回 run_id。
11. mcp/server.py：标准库 stdio JSON-RPC 2.0，支持 initialize/tools/list/tools/call，
    暴露 search_recipes 与 get_shelf_life。
12. tests：不依赖真实 LLM，覆盖 2-gram、分级与计量、五步流水线（有 trace、citations 非空）、统计公式。

自检必须实际执行并贴输出：pytest -q；tokenize('西兰花炒鸡蛋')。
```

**设计要点**：把「Agent 五步」写成**带状态落库的状态机**而不是一段 prompt——这是评分表 8 分项唯一能拿出证据的形态（trace 面板可回放）。

## 6. D · 种子数据

```
只写 apps/server/app/data/**。
1. items.json：60 种中国家庭常见食材，字段 id/name/category/shelf_life_days/carbon_kg_per_kg/
   price_per_kg/avg_grams/storage_tip/unit；数值必须合理（叶菜 3-5 天、鸡蛋 30 天、冷冻肉 90 天；
   牛肉碳足迹远高于蔬菜），不要雷同。
2. recipes.json：30 道家常快手菜，ingredients 的 name 必须与 items.json 完全一致或标 optional:true；
   至少 10 道用得上叶菜/番茄/鸡蛋/豆腐/鸡胸肉。
3. tips.md：20 条保存技巧，## 分节，每节 60-120 字，要具体（温度/容器/洗不洗/能放几天）。
4. fixtures/recognize_fridge.json：8 项，含 1 项置信度 0.55、1 项不在食材库（用于演示 warnings 与校对）。
5. fixtures/suggest.json：3 条，recipe_id 必须真实存在，含 reason/missing/citations/score。
6. README.md：数据来源、估算边界、更新方式。

自检：断言 items 名称唯一、recipes 食材全部可匹配（调味料可选），打印条数与碳因子量级。
```

**设计要点**：fixtures 里故意埋「低置信度」和「库外食材」两条坏数据——**演示素材必须能演到设计意图**，否则「人工校对」这条安全设计在视频里看不见。

## 8. R · 独立审查（每次交付前必跑）

```
你是独立审查者，不参与开发，也不知道开发过程中的自我评价与结论。
只依据文件内容、契约与工作区规范做判定。

仓库：E:\AI\AgentWorkSpace\projects\chuanzhi-aiweb
必读：工作区根 AGENTS.md（§1.6 代码规范、§1.7 审查要求）、docs/03-定稿与契约.md
范围：当前已落库的全部代码与文档（apps/server、apps/web、docs、PLAN.md、README）

检查项：
1. 契约一致性：路径、字段名、状态码、分级枚举、计量口径是否与 §5/§6 完全一致
2. 边界与异常：空输入、超大文件、未匹配食材、DB 锁、模型超时、并发写、重复提交
3. 安全：密钥是否只在 .env、日志是否脱敏、上传类型与大小、路径穿越、限流与鉴权开关
4. 回滚：是否一条命令可回退（代码、数据库、部署三层分别判）
5. 文档与实现一致性：视频脚本里的数字/功能/交互，文档声称的都必须能在代码里找到
6. 代码规范：绝对路径、魔法数字、命名、类型标注、单文件行数
7. 测试有效性：断言是否真的能失败（空断言、只测 happy path 均为缺陷）
8. 提交历史：是否按模块细粒度、message 是否能看懂做了什么

输出：缺陷清单，每条给 文件:行 + 期望行为 + 严重级别（阻塞/重要/建议）。
禁止「整体不错」这类评价；没有问题的项也要列出来说明检查过。
```

**设计要点**：审查提示词里明确「不知道开发过程的自我评价」，避免审查者被主会话的结论带偏；要求给到 `文件:行`，杜绝泛泛而谈。

## 9. 提示词设计原则

| 原则 | 原因 |
|---|---|
| 先写契约再开代理 | 并行开发唯一的对齐手段；口头约定必然漂移 |
| 目录所有权写进提示词 | 多代理同时写代码，越界即冲突 |
| 每个代理自带验收命令 | 交付物可验证，不靠「我觉得完成了」 |
| 禁止 git 操作 | 并发提交会抢 index.lock，提交统一由主会话做 |
| 要求报告「已知缺口」 | 让缺口显式化，而不是埋在代码里 |
| 禁止硬编码盘符 | 代码要在服务器（Linux）上跑 |
| 审查者隔离 | 独立上下文，避免自我确认偏误 |

## 10. 复现方式

1. 读 `docs/03-定稿与契约.md` 了解接口与边界
2. 按 §3–§7 依次把提示词交给各自的代理（可并行，目录不重叠）
3. 每个代理返回后，按契约 §12 逐条跑验收命令
4. 按 §8 跑独立审查，缺陷修完再提交
5. `git log` 可见按模块的细粒度提交，与本文件一一对应
